Objective 1.1: Understand cybersecurity concepts

หัวข้อนี้ว่าด้วยรากฐานที่สำคัญที่สุดของความมั่นคงปลอดภัยสารสนเทศ การเข้าใจว่าเรากำลังปกป้องอะไร จากภัยคุกคามใด ด้วยหลักการและกลไกพื้นฐานอย่างไร

1.1.1 Core Security Concepts & Assets

Information Security (InfoSec) คือการปกป้องข้อมูลและระบบสารสนเทศจากการเข้าถึง การเปิดเผย การแก้ไข การทำลาย หรือการหยุดชะงักโดยไม่ได้รับอนุญาต โดยต้องรักษาสมดุลระหว่าง ความปลอดภัย (Security) กับ ความต้องการและความคล่องตัวทางธุรกิจ (Business Needs)

คำศัพท์รากฐานที่ต้องแยกความหมายให้ชัดเจน:

คำศัพท์คำจำกัดความตัวอย่างในโลกจริง
Asset(ทรัพย์สิน)
สิ่งที่มีคุณค่าต่อองค์กร ซึ่งหากสูญหาย เสียหาย หรือรั่วไหลจะเกิดผลกระทบฐานข้อมูลลูกค้า (Customer Database), ระบบชำระเงิน, ทรัพย์สินทางปัญญา, บุคลากร
Threat(ภัยคุกคาม)
สิ่ง เหตุการณ์ หรือบุคคลที่อาจก่อให้เกิดอันตรายหรือสร้างความเสียหายต่อ Assetแฮกเกอร์, มัลแวร์, แรนซัมแวร์, ไฟไหม้, น้ำท่วม, ไฟดับ
Threat Actor(ผู้ก่อภัยคุกคาม)
ตัวบุคคลหรือกลุ่มบุคคลที่ลงมือหรือพยายามก่อให้เกิดภัยคุกคามอาชญากรไซเบอร์ (Cybercriminals), พนักงานภายในที่ประสงค์ร้าย (Insider Threats), รัฐสนับสนุน (Nation-State)
Vulnerability(ช่องโหว่)
จุดอ่อนหรือข้อบกพร่องในระบบ กระบวนการ หรือมาตรการควบคุม ที่ผู้ก่อภัยคุกคามอาจใช้ประโยชน์ หรือเหตุการณ์คุกคามอาจกระตุ้นให้เกิดความเสียหายเซิร์ฟเวอร์ที่ยังไม่ได้ติดตั้ง Patch, การตั้งค่าความปลอดภัยผิดพลาด (Misconfiguration), รหัสผ่านที่คาดเดาง่าย
Exploit(การใช้ประโยชน์จากช่องโหว่)
วิธีการ โค้ดโปรแกรม หรือเทคนิคที่ใช้เจาะผ่านจุดอ่อนของระบบสคริปต์ยิงเจาะช่องโหว่ซอฟต์แวร์, Phishing Email หลอกขอรหัสผ่าน
Risk(ความเสี่ยง)
โอกาสและผลกระทบของความเสียหายที่อาจเกิดขึ้นเมื่อ Threat อาศัย Vulnerability สร้างผลกระทบต่อ Assetโอกาสที่ฐานข้อมูลลูกค้าจะถูกขโมยและสร้างผลเสียหายทางการเงินและชื่อเสียง
Control / Safeguard(มาตรการควบคุม)
กลไก นโยบาย หรือเทคโนโลยีที่นำมาติดตั้งเพื่อลดโอกาสหรือผลกระทบของความเสี่ยงMulti-Factor Authentication (MFA), Firewall, นโยบายความปลอดภัย

↓ หากสำเร็จจะก่อให้เกิด ↓

ข้อควรระวังสำหรับข้อสอบ
Threat ไม่ใช่ Vulnerability

Threat คือบุคคล สิ่ง หรือเหตุการณ์ที่อาจก่อความเสียหาย ทั้งจากภายในและภายนอกองค์กร (เช่น พนักงานประสงค์ร้าย, Hacker, Flood) ส่วน Vulnerability คือจุดอ่อนภายในระบบของเรา (เช่น Unpatched Server หรือ Misconfiguration)

Vulnerability ไม่ได้แปลว่าเกิดเหตุโจมตีแล้ว

การมีจุดอ่อนในระบบไม่ได้แปลว่าองค์กรถูกแฮกแล้ว หากไม่มี Threat เข้ามาใช้ประโยชน์จากช่องโหว่นั้น หรือมี Control ชดเชยอื่นปิดกั้นไว้

1.1.2 The CIA Triad — Confidentiality, Integrity, Availability

แกนกลางของ Information Security ทุกเรื่องถูกสร้างขึ้นบนเสาหลัก 3 ต้น เรียกว่า CIA Triad

Core Model

The CIA Triad — Three Pillars of Information Security

THE CIA TRIAD · 3 PILLARS

สามเสาหลักแห่งความมั่นคงปลอดภัยสารสนเทศ: ความลับ · ความถูกต้องสมบูรณ์ · ความพร้อมใช้งาน

C
CONFIDENTIALITY (การรักษาความลับ)
"Who can SEE it?" · ป้องกันการเปิดเผยโดยไม่ได้รับอนุญาต

รักษาข้อมูลไม่ให้รั่วไหลสู่บุคคลที่ไม่เกี่ยวข้อง: การเข้ารหัส (AES-256), การกำหนดสิทธิ์ตามบทบาท (RBAC), สิทธิ์ขั้นต่ำ (PoLP), นโยบายจัดชั้นความลับ (Data Classification)

I
INTEGRITY (ความถูกต้องสมบูรณ์)
"Can I TRUST it?" · ป้องกันการดัดแปลงแก้ไข

รับประกันว่าข้อมูลถูกต้อง แท้จริง และไม่ถูกเปลี่ยนแปลงโดยไม่ได้รับอนุญาต: การคำนวณแฮช (SHA-256), ลายมือชื่อดิจิทัล (Digital Signatures), การควบคุมการเปลี่ยนแปลง (Change Control)

A
AVAILABILITY (ความพร้อมใช้งาน)
"Can I ACCESS it?" · เข้าถึงได้ทันทีเมื่อจำเป็น

รับรองว่าระบบและข้อมูลพร้อมให้ผู้มีสิทธิ์ใช้งานได้ต่อเนื่อง: การกระจายภาระงาน (Load Balancing), ระบบสำรองคู่ขนาน (Redundancy / Clustering), แผนกู้คืนระบบ (Backups / DRP)

1. Confidentiality — การรักษาความลับ

ข้อมูลต้องถูกเข้าถึงและเปิดเผยต่อ ผู้ที่ได้รับอนุญาตเท่านั้น (Authorized Individuals Only) โดยมุ่งเน้นการป้องกัน Unauthorized Disclosure (การเปิดเผยข้อมูลโดยไม่ได้รับอนุญาต)

มาตรการควบคุมหลัก (Controls):

  • Encryption (การเข้ารหัสข้อมูล): แปลงข้อมูลให้อ่านไม่ออกหากไม่มีกุญแจถอดรหัส
  • Access Control & Permissions: จำกัดสิทธิ์การอ่านไฟล์และระบบ
  • Data Classification (การจัดชั้นความลับ): กำหนดระดับความลับ เช่น Public, Internal, Confidential, Restricted
  • Data Masking (การบดบังข้อมูลบางส่วน): ซ่อนข้อมูลอ่อนไหวบางส่วนเพื่อป้องกันการมองเห็น เช่น แสดงเฉพาะเลข 4 หลักสุดท้ายของบัตรเครดิต
  • Need to Know: อนุญาตให้เข้าถึงเฉพาะข้อมูลที่จำเป็นต่อการปฏิบัติหน้าที่เท่านั้น
  • Multi-Factor Authentication (MFA): ป้องกันการสวมรอยเข้าถึงข้อมูล
สถานการณ์จำลอง: แฮกเกอร์เจาะระบบขโมย Customer Database ออกไป แม้ข้อมูลจะไม่ถูกแก้ไขหรือลบทิ้ง แต่บุคคลที่ไม่ควรเห็นได้เห็น → กระทบ Confidentiality
คีย์เวิร์ดในข้อสอบ: Confidentiality = Who can SEE it? / Secret / Unauthorized Disclosure

2. Integrity — ความถูกต้องและความสมบูรณ์ของข้อมูล

ข้อมูลต้อง ไม่ถูกแก้ไข ดัดแปลง หรือทำลายโดยไม่ได้รับอนุญาต และสามารถตรวจสอบความถูกต้องได้ตลอดวงจรชีวิต เพื่อป้องกัน Unauthorized Modification / Tampering (การดัดแปลงข้อมูลโดยมิชอบ)

มาตรการควบคุมหลัก (Controls):

  • Hashing (การคำนวณค่าแฮช): ใช้สร้างค่าสรุปข้อมูลทางเดียวเพื่อตรวจสอบว่าไฟล์หรือข้อความถูกดัดแปลงหรือไม่ (เช่น SHA-256)
  • Digital Signatures (ลายมือชื่อดิจิทัล): ยืนยันทั้งความถูกต้องของข้อมูล (Integrity) และผู้ลงนาม (Authenticity)
  • Access Permissions: จำกัดสิทธิ์ในการแก้ไขหรือลบข้อมูล (Write / Delete permissions)
  • Change Management (การบริหารการเปลี่ยนแปลง): มีขั้นตอนอนุมัติ บันทึก และติดตามการแก้ไขระบบ
  • File Integrity Monitoring (FIM) & Audit Logs: ตรวจจับเมื่อมีการเปลี่ยนแปลงไฟล์สำคัญ
สถานการณ์จำลอง: ผู้โจมตีแทรกแซงฐานข้อมูลระบบธนาคารแล้วเปลี่ยนยอดเงินในบัญชี ข้อมูลยังเปิดอ่านได้ ระบบยังออนไลน์ปกติ แต่เนื้อหาถูกเปลี่ยนแปลง → กระทบ Integrity
คีย์เวิร์ดในข้อสอบ: Integrity = Can I TRUST the data? / Correct / Tampering / Alteration
จุดสับสนยอดฮิต (Hashing vs. Encryption)
Hashing (ฟังก์ชันทางเดียว — One-way)

คำนวณค่าสรุปข้อมูลเพื่อเปรียบเทียบความถูกต้อง ไม่สามารถถอดกลับมาเป็นข้อความต้นฉบับได้

Encryption (กระบวนการสองทาง — Two-way)

เข้ารหัสเพื่อให้เป็นความลับ และสามารถถอดรหัส (Decryption) กลับมาอ่านได้ด้วยกุญแจที่ถูกต้อง

3. Availability — ความพร้อมใช้งาน

ระบบ ข้อมูล และทรัพยากรต้อง พร้อมให้ผู้มีสิทธิ์เข้าใช้งานตามเวลาที่จำเป็นและข้อกำหนดบริการ โดยมีเป้าหมายสำคัญคือการลด Downtime และสนับสนุนความต่อเนื่องทางธุรกิจเมื่อเผชิญภัยคุกคาม เช่น Hardware Failure, ไฟดับ (Power Outage), การโจมตี DDoS, Ransomware เข้ารหัส, หรือภัยธรรมชาติ

มาตรการควบคุมหลัก (Controls):

  • Redundancy (ความซ้ำซ้อนของอุปกรณ์): มีชิ้นส่วนสำรอง เช่น Power Supply คู่, RAID ฮาร์ดดิสก์
  • Failover & Load Balancing: การกระจายทราฟฟิกและสลับระบบอัตโนมัติเมื่อเครื่องหลักล่ม
  • Uninterruptible Power Supply (UPS) & Backup Generators: สำรองพลังงานไฟฟ้า
  • Redundant Network / Multiple ISPs: มีผู้ให้บริการอินเทอร์เน็ตมากกว่า 1 เจ้า
  • Data Backups & Disaster Recovery (DR): มีแผนและข้อมูลสำรองสำหรับกู้คืนระบบ
คีย์เวิร์ดในข้อสอบ: Availability = Can I ACCESS it when needed? / Accessible / Downtime / Redundancy

1.1.3 Identification & Authentication (AAA)

การควบคุมการเข้าถึงระบบมีลำดับขั้นตอนที่เป็นมาตรฐาน เรียกว่า AAA Framework โดยมีขั้นตอนตั้งต้นคือ Identification

Process Flow

The AAA Framework & Identity Lifecycle

AAA SECURITY FRAMEWORK

วงจร 4 ขั้นตอนในการเข้าถึงระบบอย่างปลอดภัย: ระบุตัวตน → พิสูจน์ตัวตน → อนุญาตสิทธิ์ → บันทึกประวัติ

01
IDENTIFICATION (การระบุตัวตน)
"Who are you?" · การอ้างสิทธิ์ในตัวตน

ผู้ใช้แจ้งตัวตนต่อระบบ เช่น Username, Employee ID, อีเมล (ยังไม่มีการพิสูจน์ความจริงในขั้นตอนนี้)

↓ นำหลักฐานมาพิสูจน์ ↓
02
AUTHENTICATION (การพิสูจน์ตัวตน)
"Prove it!" · ตรวจสอบหลักฐานความจริง

ระบบตรวจสอบหลักฐานว่าเป็นตัวจริง: รหัสผ่าน (Knowledge), Token / OTP (Ownership), ลายนิ้วมือ/ใบหน้า (Inherence) · MFA ใช้ 2 ปัจจัยขึ้นไปที่ต่างหมวดหมู่

↓ กำหนดขอบเขตสิทธิ์ ↓
03
AUTHORIZATION (การอนุญาตสิทธิ์)
"What can you do?" · การอนุญาตเข้าถึง

กำหนดว่าผู้ใช้ทำอะไรได้บ้างในระบบ: Access Control Lists (ACLs), บทบาทงาน (RBAC) ตามหลักสิทธิ์ขั้นต่ำที่จำเป็น (Least Privilege)

↓ บันทึกและติดตามผล ↓
04
ACCOUNTING & AUDITING (การตรวจสอบ)
"What did you do?" · การบันทึกและตรวจสอบประวัติ

Audit Trails และ Timestamps ช่วยติดตามกิจกรรมและสนับสนุน Accountability เมื่อบันทึกได้รับการปกป้องและเชื่อมโยงกับตัวตนอย่างน่าเชื่อถือ ส่วน Non-repudiation ต้องมีหลักฐานและการควบคุมที่เหมาะสมต่อการโต้แย้งภายหลัง เช่น ลายมือชื่อดิจิทัลพร้อมการจัดการกุญแจและหลักฐานที่เชื่อถือได้ ไม่ได้เกิดจากการมี Log เพียงอย่างเดียว

1. Identification — การระบุตัวตน

ขั้นตอนที่ผู้ใช้ กล่าวอ้างว่าตนเองคือใคร (Claiming Identity) เช่น การกรอก Username, การป้อน User ID, หรือการแตะบัตรพนักงาน

หมายเหตุสำคัญ: Identification ยังไม่ใช่การพิสูจน์ความจริง เป็นเพียงแค่การบอกชื่อหรือตัวตนเท่านั้น

2. Authentication — การพิสูจน์ตัวตน

ขั้นตอนที่ระบบ ตรวจสอบและพิสูจน์ว่าผู้ใช้เป็นบุคคลนั้นจริงตามที่กล่าวอ้าง (Proving Identity) เช่น การตรวจสอบ Password, การตรวจลายนิ้วมือ, หรือการรับรหัส OTP

1.1.4 Multi-Factor Authentication (MFA)

MFA คือการพิสูจน์ตัวตนโดยใช้ปัจจัยตั้งแต่ 2 ประเภทที่แตกต่างกันขึ้นไป (Two or More Independent Factors)

ปัจจัยหลักของ MFA มี 3 ประเภท: Know, Have และ Are; สถานที่หรือเครือข่ายเป็นบริบทเสริม (Context) ไม่ใช่ปัจจัยอิสระที่ใช้แทนประเภทเหล่านี้:

01

Something You Know

สิ่งที่คุณรู้ (Knowledge)

ข้อมูลหรือความลับที่อยู่ในสมองของผู้ใช้

ตัวอย่าง: Password, PIN, Passphrase; Security Questions เป็นตัวอย่าง Knowledge แบบเดิมที่คาดเดาหรือสืบค้นคำตอบได้ ไม่ใช่แนวทางสมัยใหม่ที่แนะนำ
จุดอ่อน: เสี่ยงต่อการถูกเดา (Brute Force), แอบดู (Shoulder Surfing), หรือ Phishing
02

Something You Have

สิ่งที่คุณมี (Possession)

วัตถุทางกายภาพที่ผู้ใช้เป็นผู้ครอบครองจริง

ตัวอย่าง: Smart Card, Hardware Token (RSA SecurID), FIDO2 Security Key (YubiKey), สมาร์ตโฟนรับ Authenticator App / SMS OTP
03

Something You Are

สิ่งที่คุณเป็น (Inherence / ชีวมิติ)

คุณลักษณะทางชีวภาพหรือสรีรวิทยาเฉพาะบุคคล (Biometrics)

ตัวอย่าง: ลายนิ้วมือ (Fingerprint), สแกนใบหน้า (Face Recognition), สแกนม่านตา (Iris Scan), ลายเสียง (Voiceprint)
04

Somewhere You Are

สถานที่ที่คุณอยู่ (Location Context)

บริบททางภูมิศาสตร์หรือตำแหน่งเครือข่ายที่ตรวจสอบได้

ตัวอย่าง: พิกัด GPS, IP Geolocation, การล็อกอินจากเครือข่ายสำนักงาน (Corporate IP Subnet)
หมายเหตุ: เป็นบริบทเสริมสำหรับประเมินความเสี่ยง (Supplementary Risk Signal) ไม่ใช่ปัจจัย MFA; Password + Corporate IP เพียงอย่างเดียวยังไม่ใช่ MFA
กับดักข้อสอบที่พบบ่อยที่สุด (Multi-Factor vs. Multi-Credential)
Username + Password + PIN (ไม่ใช่ MFA!)

ทั้ง Password และ PIN จัดอยู่ในหมวด Something You Know ทั้งคู่ จึงถือเป็นเพียง Multi-Credential ไม่ใช่ Multi-Factor

Password + ลายนิ้วมือ (เป็น MFA!)

เป็นการผสมผสานระหว่าง Something You Know กับ Something You Are (คนละหมวดหมู่กันอย่างแท้จริง)

1.1.5 Authorization & Accounting

3. Authorization — การกำหนดและอนุญาตสิทธิ์

เกิดขึ้น หลังจาก Authentication สำเร็จในตัวอย่างการล็อกอินทั่วไป ทั้งนี้นโยบาย Authorization อาจอนุญาตผู้ใช้ที่ยังไม่ล็อกอินให้อ่านข้อมูลสาธารณะได้ ระบบจะตัดสินใจว่าผู้ใช้คนนี้มีสิทธิ์ทำอะไรกับทรัพยากรใดได้บ้าง (Permissions / Privileges)

  • นาย A ล็อกอินผ่าน (Authentication สำเร็จ)
  • นาย A อ่านไฟล์รายงานยอดขายได้ (Read Authorized)
  • นาย A พยายามลบไฟล์ระบบ แต่ระบบปฏิเสธ (Delete Unauthorized)

4. Accounting (Auditing) — การบันทึกและตรวจสอบย้อนหลัง

การบันทึก ติดตาม และเก็บบันทึกประวัติกิจกรรมทั้งหมด (Tracking & Logging Activities) เพื่อบันทึกข้อมูลสำคัญ: ใครทำอะไร ที่ไหน เมื่อไร และเกิดผลลัพธ์อย่างไร (Who, What, When, Where, Success/Failure) เช่น System Event Logs, Access Logs, Network Flow Logs, และ Audit Trails

วัตถุประสงค์หลักคือการใช้ในการสืบสวนคดีความมั่นคงปลอดภัย (Forensics), เฝ้าระวังความผิดปกติ, และสร้าง Accountability ที่ตรวจสอบย้อนหลังได้

สรุปคำถามหลักในข้อสอบสำหรับ 4 ขั้นตอน AAA:

คำถามหลักในข้อสอบขั้นตอนที่เกี่ยวข้อง
"Who are you?"Identification
"Prove that you are who you claim to be."Authentication
"What actions and resources are you permitted to access?"Authorization
"What did you do, and what evidence is recorded?"Accounting

1.1.6 Non-repudiation, Privacy & Data Protection

1. Non-repudiation — การไม่อาจปฏิเสธความรับผิดชอบได้

ความสามารถในการพิสูจน์ได้อย่างน่าเชื่อถือว่า มีบุคคลใดบุคคลหนึ่งได้กระทำการหรือส่งข้อมูลนั้นจริง โดยผู้กระทำไม่สามารถอ้างภายหลังได้ว่าตนเองไม่ได้เป็นผู้ทำ โดยอาศัยกลไกสำคัญคือ Digital Signature ร่วมกับโครงสร้างกุญแจสาธารณะ (PKI) และการประทับเวลาที่เชื่อถือได้ (Timestamping)

ความต่างจาก Authentication: Authentication พิสูจน์ตัวตน ณ ขณะล็อกอิน ส่วน Non-repudiation สร้างหลักฐานทางนิติวิทยาศาสตร์ที่ผูกมัดการกระทำในอดีต

2. Privacy — การคุ้มครองความเป็นส่วนตัวของข้อมูล

เกี่ยวข้องกับการคุ้มครอง Personally Identifiable Information (PII) / Personal Data ตลอดวงจรชีวิต: การเก็บรวบรวมข้อมูล (Collection), การประมวลผล (Processing), การจัดเก็บรักษา (Storage), การถ่ายโอน (Transfer), และการทำลาย (Disposal)

3 บทบาทหลักในกฎหมายคุ้มครองข้อมูลส่วนบุคคล (เช่น GDPR, PDPA):

Data Subject (เจ้าของข้อมูลส่วนบุคคล)

บุคคลธรรมดาที่ข้อมูลนั้นระบุไปถึง (เช่น นายสมชาย ลูกค้าของบริษัท หรือพนักงานในองค์กร)

Data Controller (ผู้ควบคุมข้อมูล)

บุคคลธรรมดา นิติบุคคล หน่วยงาน หรือองค์กรที่กำหนดโดยลำพังหรือร่วมกับผู้อื่นว่า จะเก็บข้อมูลทำไม และประมวลผลอย่างไร (Determines Purpose and Means) เช่น บริษัทค้าปลีกที่เก็บข้อมูลลูกค้า

Data Processor (ผู้ประมวลผลข้อมูล)

ฝ่ายที่ทำการประมวลผลข้อมูล ในนามของและตามคำสั่งของผู้ควบคุมข้อมูล (Processes on behalf of Controller) เช่น บริษัท Cloud Provider ที่รับฝากฐานข้อมูล

Data Inventory

รายการสำรวจทรัพย์สินข้อมูลทั้งหมดขององค์กร เพื่อตอบคำถามว่า "เรามีข้อมูลประเภทใดบ้าง และจัดเก็บอยู่ที่ใด?"

Data Retention

นโยบายระบุระยะเวลาในการเก็บรักษาข้อมูลแต่ละประเภท และกำหนดเงื่อนไขการทำลายทิ้งเมื่อหมดความจำเป็น (เช่น การเก็บเอกสารภาษีพนักงานไว้ 7 ปีตามที่กฎหมายกำหนด)

Right to Be Forgotten (สิทธิในการขอลบข้อมูล)

สิทธิของ Data Subject ในการร้องขอให้ลบข้อมูลส่วนบุคคลของตน อย่างไรก็ตาม ไม่ได้แปลว่าขอลบแล้วองค์กรต้องลบทันทีเสมอไป หากมีกฎหมายบังคับให้ต้องเก็บรักษาไว้ (เช่น กฎหมายภาษี กฎหมายฟอกเงิน) องค์กรยังมีความชอบธรรมในการเก็บข้อมูลนั้นตามกรอบกฎหมาย

3. Accountability — ความรับผิดชอบที่ตรวจสอบย้อนหลังได้

หลักการที่บุคคลต้องรับผิดชอบต่อการกระทำของตนบนระบบ โดยระบบต้องสามารถเชื่อมโยงกิจกรรมไปยังตัวบุคคลนั้นได้อย่างจำเพาะเจาะจง (Unique Identity + Secure Logs)

สรุปเปรียบเทียบคำที่ใกล้เคียงกัน
Confidentiality

ข้อมูลลับถูกจำกัดการเข้าถึงเฉพาะผู้ได้รับอนุญาต (Who can SEE it?)

Privacy

การจัดการข้อมูลส่วนบุคคล (PII) ให้สอดคล้องกับสิทธิและกฎหมาย

Non-repudiation

มีหลักฐานทางดิจิทัลยืนยันว่าผู้กระทำไม่อาจปฏิเสธได้

Accountability

สามารถตรวจสอบย้อนหลังได้ว่าใครเป็นผู้รับผิดชอบต่อเหตุการณ์นั้น (Unique Identity + Secure Logs)

1.1.7 Zero Trust & Defense in Depth

สองแนวคิดทางสถาปัตยกรรมความปลอดภัยที่เสริมส่งซึ่งกันและกันแต่มีมุมมองที่ต่างกัน:

1. Zero Trust Architecture

ยึดถือคติพจน์สำคัญคือ “Never Trust, Always Verify” (ไม่ไว้วางใจใคร ตรวจสอบยืนยันเสมอ) โดยปฏิเสธแนวคิดความเชื่อถือแบบเดิมที่ว่า "คนในเครือข่ายภายใน (Internal Network) ปลอดภัยและเชื่อถือได้"

หลักการสำคัญของ Zero Trust:

  • ยืนยันตัวตนและอุปกรณ์ตามบริบททุกครั้งที่มีการร้องขอเข้าถึง
  • ยึดหลัก Least Privilege (สิทธิ์เท่าที่จำเป็น)
  • แบ่งส่วนเครือข่ายอย่างละเอียด (Micro-segmentation)
  • ประเมินพฤติกรรมและความเสี่ยงแบบเรียลไทม์อย่างต่อเนื่อง
ตัวอย่างสถานการณ์จริง: แม้พนักงานจะนั่งทำงานในออฟฟิศและเชื่อมต่อสาย LAN ของบริษัท แต่เมื่อจะเปิดฐานข้อมูลลูกค้า ระบบยังคงต้องบังคับให้ยืนยันตัวตน ตรวจสอบสิทธิ์ และประเมินความปลอดภัยของเครื่องคอมพิวเตอร์ใหม่อยู่เสมอ

2. Defense in Depth (Layered Defense)

กลยุทธ์การวาง มาตรการควบคุมความปลอดภัยหลายชั้นที่สอดประสานกัน (Defense in Depth) เพื่อลดโอกาสที่ความล้มเหลวของมาตรการเดียวจะนำไปสู่ความเสียหาย ชั้นต่าง ๆ ยังอาจมีจุดพึ่งพาร่วมกัน จึงไม่รับประกันว่าจะกำจัดจุดล้มเหลวเดี่ยว (Single Point of Failure) ทั้งหมด

Objective 1.2: Understand risk management concepts

การบริหารความเสี่ยงคือหัวใจของการตัดสินใจด้านความปลอดภัย องค์กรไม่สามารถกำจัดความเสี่ยงให้เป็นศูนย์ได้ แต่ต้องเข้าใจ วัดผล และจัดการให้อยู่ในระดับที่ยอมรับได้

1.2.1 Risk Definition & Core Components

Risk (ความเสี่ยง) ประเมินจากโอกาสที่เหตุการณ์ไม่พึงประสงค์จะเกิดขึ้นร่วมกับขนาดของผลกระทบหรือความเสียหายที่เกิดขึ้นต่อองค์กร

องค์ประกอบหลักของความเสี่ยง:

Likelihood (Probability / โอกาสเกิด)

ความเป็นไปได้ที่ภัยคุกคามจะอาศัยช่องโหว่โจมตีสำเร็จ

Impact (Magnitude / ผลกระทบ)

ระดับความรุนแรงหรือมูลค่าความเสียหายที่องค์กรต้องสูญเสีย (ทางการเงิน การดำเนินงาน กฎหมาย หรือชื่อเสียง)

Risk Level (ระดับความเสี่ยง)

ผลลัพธ์จากการนำโอกาสเกิดและผลกระทบมาประเมินร่วมกันเพื่อจัดลำดับความสำคัญ

สมการความเสี่ยงเชิงคุณภาพ (Qualitative Risk Formula):

Risk ≈ Likelihood × Impact

บางโมเดลแบบง่ายใช้ผลคูณนี้โดยต้องกำหนดสเกลและความหมายของคะแนนให้ชัดเจน องค์กรอาจเลือกวิธีเชิงคุณภาพหรือเชิงปริมาณต่างกัน ไม่ใช่สูตรเดียวที่บังคับใช้กับทุกการประเมิน

1.2.2 Quantitative Risk Analysis & Formulas

การวิเคราะห์ความเสี่ยงเชิงปริมาณ (Quantitative Risk Analysis) เป็นการคำนวณมูลค่าความเสียหายออกมาเป็นตัวเลขทางการเงินที่ชัดเจน มีสูตรและตัวแปรสำคัญที่ ต้องจำอย่างแม่นยำ:

ตัวแปรพื้นฐานในการคำนวณ

Asset Value (AV)

มูลค่ารวมของทรัพย์สินที่กำลังพิจารณา (คิดเป็นจำนวนเงิน เช่น มูลค่าเซิร์ฟเวอร์ฐานข้อมูล = \$10,000)

Exposure Factor (EF)

สัดส่วนหรือเปอร์เซ็นต์ความเสียหายที่คาดว่าจะเกิดขึ้นต่อ Asset เมื่อเกิดเหตุการณ์ร้ายแรง 1 ครั้ง (แสดงเป็นค่าร้อยละ เช่น เสียหาย 50% หรือ 0.50)

1. Single Loss Expectancy (SLE)

ความเสียหายทางการเงินที่คาดว่าจะเกิดขึ้นจาก การเกิดเหตุการณ์ครั้งเดียว (Single Incident)

Single Loss Expectancy (SLE) ความเสียหายต่อครั้ง

SLE = AV × EF

AV: Asset Value (มูลค่าทรัพย์สิน เช่น \$10,000)
EF: Exposure Factor (สัดส่วนความเสียหาย เช่น 50% หรือ 0.50)
ตัวอย่างการคำนวณ SLE:
  • เซิร์ฟเวอร์มีมูลค่า (AV) = $10,000
  • หากน้ำท่วมห้องเซิร์ฟเวอร์ ประเมินว่าจะเสียหาย (EF) = 50% (0.50)
  • SLE = $10,000 × 0.50 = $5,000 ต่อครั้ง

2. Annualized Rate of Occurrence (ARO)

ความถี่หรือจำนวนครั้งโดยประมาณที่เหตุการณ์นั้นจะเกิดขึ้น ภายในรอบระยะเวลา 1 ปี

ตัวอย่างค่า ARO ในข้อสอบ:

  • เกิดขึ้นปีละ 2 ครั้ง → ARO = 2
  • เกิดขึ้นปีละ 1 ครั้ง → ARO = 1
  • เกิดขึ้นทุก ๆ 2 ปีครั้ง → ARO = 1 / 2 = 0.5
  • เกิดขึ้นทุก ๆ 5 ปีครั้ง → ARO = 1 / 5 = 0.2
  • เกิดขึ้นทุก ๆ 10 ปีครั้ง → ARO = 1 / 10 = 0.1

3. Annualized Loss Expectancy (ALE)

ประมาณการมูลค่าความเสียหายทางการเงินทั้งหมดที่คาดว่าจะเกิดขึ้น เฉลี่ยต่อปี (Loss per Year)

Annualized Loss Expectancy (ALE) ความเสียหายเฉลี่ยต่อปี

ALE = SLE × ARO

SLE: Single Loss Expectancy (ความเสียหายต่อครั้ง เช่น \$5,000)
ARO: Annualized Rate of Occurrence (ความถี่ต่อปี เช่น 2 ครั้ง/ปี)
ตัวอย่างคำนวณต่อเนื่อง ALE:
  • จากตัวอย่างข้างต้น SLE = $5,000
  • หากประเมินว่าเหตุการณ์นี้อาจเกิดขึ้นปีละ 2 ครั้ง (ARO = 2) → ALE = $5,000 × 2 = $10,000 ต่อปี
  • หากเหตุการณ์นี้เกิดขึ้นทุก 5 ปีครั้ง (ARO = 0.2) → ALE = $5,000 × 0.2 = $1,000 ต่อปี

• EF (Exposure Factor): อัตราส่วนความเสียหายจากเหตุการณ์ (เช่น เสียหาย 40% = 0.40)
• ผลลัพธ์ SLE: $100,000 × 0.40 = $40,000 ต่อครั้ง

SLE × ARO → ALE

• ARO (Annualized Rate of Occurrence): ความถี่ที่คาดว่าจะเกิดเหตุใน 1 ปี (เช่น เกิด 0.5 ครั้ง/ปี หรือ 2 ปีครั้ง)
• ผลลัพธ์ ALE: $40,000 × 0.5 = $20,000 ต่อปี

RULE
COST-BENEFIT ANALYSIS (CBA)
Decision Rule · ความคุ้มค่าของมาตรการควบคุม

การเปรียบเทียบด้านการเงินแบบง่าย: ALE Savings = ALE ก่อน − ALE หลัง เปรียบเทียบกับต้นทุน Control ต่อปี ตัวอย่าง ALE 20,000/ปี กับ Control 25,000/ปี ไม่คุ้มเมื่อพิจารณาเฉพาะการลดความเสียหายนี้ แต่กฎหมาย สัญญา ความปลอดภัยของบุคคล และภารกิจอาจกำหนดให้ต้องใช้มาตรการแม้ผลประโยชน์สุทธิทางการเงินไม่เป็นบวก

ประโยชน์หลักในการทำข้อสอบ (Cost-Benefit Decision Rule)

ค่า ALE ถูกนำมาใช้เปรียบเทียบกับ ต้นทุนของมาตรการควบคุม (Cost of Control / Safeguard Cost)

การเปรียบเทียบด้านการเงินแบบง่าย: ผลประโยชน์จากการลดความเสียหายต่อปี (Annual Loss-Reduction Benefit) = ALE ก่อนใช้ Control − ALE หลังใช้ Control แล้วเปรียบเทียบกับต้นทุน Control ต่อปี การมีต้นทุนต่ำกว่า ALE เดิมเพียงอย่างเดียวยังไม่พอ เช่น ALE ก่อน 10,000/ปี หลัง 9,000/ปี ลดความเสียหายได้ 1,000/ปี หาก Control มีต้นทุน 5,000/ปี ผลประโยชน์สุทธิเท่ากับ −4,000/ปี ตัวอย่างเดิมที่ ALE \$10,000/ปี แต่ Control ราคา \$25,000/ปี ก็ไม่คุ้มด้านการเงินภายใต้สมมติฐานนี้ อย่างไรก็ตาม กฎหมาย สัญญา ความปลอดภัยของบุคคล และภารกิจอาจทำให้องค์กรต้องเลือกมาตรการแม้ผลตอบแทนทางการเงินโดยตรงไม่เป็นบวก

  2. Risk Assessment & Analysis: วิเคราะห์และจัดลำดับความสำคัญของความเสี่ยง (Qualitative: สูง/กลาง/ต่ำ, Quantitative: คำนวณ SLE/ALE)
  3. Risk Treatment / Response: ตัดสินใจเลือกแนวทางรับมือความเสี่ยงที่เหมาะสม (Avoidance, Mitigation, Transfer, Acceptance)
  4. Risk Monitoring & Review: ติดตามประสิทธิภาพของมาตรการควบคุมอย่างต่อเนื่อง และทบทวนเมื่อเกิดเหตุการณ์กระตุ้น (Trigger Events) เช่น:
    • มีการนำเทคโนโลยีใหม่มาใช้งาน (New Technology)
    • มีการอัปเกรดระบบซอฟต์แวร์ครั้งใหญ่ (Major Software Upgrade)
    • มีกฎหมายหรือข้อบังคับใหม่ประกาศใช้ (New Laws or Regulations)
    • มีภัยคุกคามหรือช่องโหว่ใหม่ปรากฏขึ้น (Emerging Threats / Zero-day Vulnerabilities)
  5. Risk Communication & Reporting: รวบรวมข้อมูลสถานะความเสี่ยง รายงานต่อคณะผู้บริหารและผู้มีส่วนได้เสีย (Stakeholders) เพื่อให้สามารถตัดสินใจจัดสรรทรัพยากรได้อย่างเหมาะสม
ข้อสังเกตเชิงโครงสร้างและวิชาการ (4 vs. 5 Lifecycle Stages)

บทนี้ใช้ลำดับช่วยเรียนรู้ 5 ส่วนจากบันทึกการเรียน: Identify → Assess → Treat → Monitor → Communicate/Report โดยการสื่อสารและรายงานผลเกิดควบคู่ได้ตลอดกระบวนการ เพื่อให้ผู้บริหารและผู้มีส่วนได้เสียตัดสินใจจัดสรรทรัพยากรได้ กรอบงานอื่นอาจจัดกลุ่มต่างกัน เช่น NIST SP 800-39 ใช้ Frame, Assess, Respond และ Monitor ลำดับ 5 ส่วนนี้เป็นแบบจำลองช่วยเรียนรู้ ไม่ใช่ข้อกำหนดลำดับตายตัวจาก Exam Outline

1.2.4 Risk Treatment: The 4 Responses

เมื่อประเมินความเสี่ยงแล้ว องค์กรต้องเลือกกลยุทธ์ในการจัดการความเสี่ยง 4 รูปแบบหลัก:

01

Risk Avoidance (การหลีกเลี่ยงความเสี่ยง)

Stop Doing It

ยกเลิกกิจกรรม ยุติการใช้ระบบ หรือเปลี่ยนแนวทางใหม่ทั้งหมด เพื่อกำจัดความเสี่ยงนั้นให้หมดสิ้นไปโดยสิ้นเชิง (Eliminate Risk completely)

ตัวอย่างในโลกจริง: ยกเลิกการให้บริการในประเทศหรือพื้นที่ที่มีความเสี่ยงสงครามหรือภัยคุกคามไซเบอร์สูงมาก หรือหยุดใช้งานซอฟต์แวร์ของผู้จำหน่ายที่มีช่องโหว่ร้ายแรงและไม่ยอมออก Patch
คีย์เวิร์ดในข้อสอบ: Eliminate, Terminate, Drop, Cancel activity, Stop service
02

Risk Mitigation (การลดความเสี่ยง)

Reduce Risk

การติดตั้งและบังคับใช้มาตรการควบคุมความปลอดภัย (Controls / Safeguards) เพื่อลดโอกาสเกิด (Likelihood) หรือลดขนาดผลกระทบ (Impact) ให้อยู่ในระดับที่องค์กรยอมรับได้

ตัวอย่างในโลกจริง: ติดตั้ง Next-Gen Firewall, บังคับใช้ MFA ทุกการเข้าสู่ระบบ, ติดตั้ง Antivirus/EDR บนเครื่องผู้ใช้, อุดช่องโหว่ระบบ (Patch Management) อย่างสม่ำเสมอ
คีย์เวิร์ดในข้อสอบ: Implement safeguards, Controls, Reduce, Lower likelihood/impact
03

Risk Transfer / Sharing (การโอนความเสี่ยง)

Shift Financial Burden

การถ่ายโอนหรือแบ่งเบาภาระผลกระทบ (โดยเฉพาะความเสียหายทางการเงิน) ไปยังบุคคลภายนอก เช่น การทำประกันภัย หรือการทำสัญญาจ้างบริการ

ตัวอย่างในโลกจริง: การซื้อกรมธรรม์ประกันภัยไซเบอร์ (Cyber Insurance) เพื่อชดเชยค่าสินไหม หรือการทำสัญญากับ Cloud Provider / MSSP พร้อมข้อตกลงระดับการให้บริการ (SLA)
คีย์เวิร์ดในข้อสอบ: Cyber Insurance, Warranty, Third-party contract, Financial shift
04

Risk Acceptance (การยอมรับความเสี่ยง)

Live With It

รับรู้และยินยอมรับความเสี่ยงนั้นไว้โดยไม่ติดตั้งมาตรการควบคุมเพิ่มเติม มักใช้เมื่อระดับความเสี่ยงต่ำมาก หรือต้นทุนในการป้องกันสูงกว่าประโยชน์จากการลดความเสียหาย (Annual Control Cost > ALE Before − ALE After) โดยต้องพิจารณากฎหมาย สัญญา ความปลอดภัย และภารกิจก่อนรับความเสี่ยง

ตัวอย่างในโลกจริง: เซิร์ฟเวอร์ทดสอบภายในไม่มีข้อมูลสำคัญและมี ALE เพียง $50/ปี หากซื้ออุปกรณ์ป้องกันราคา $2,000/ปี จึงไม่คุ้มค่า ผู้บริหารจึงลงนามอนุมัติรับความเสี่ยงอย่างเป็นทางการ
คีย์เวิร์ดในข้อสอบ: Acknowledge, Retain, Tolerate, Formal executive sign-off, Low risk
ประเด็นเน้นย้ำสำหรับข้อสอบ (Cyber Insurance Limitation)
การซื้อประกันภัยไซเบอร์ (Cyber Insurance) ช่วยโอนเฉพาะภาระค่าเสียหายทางการเงิน (Financial Impact)

ช่วยชดเชยความเสียหายทางการเงินตามวงเงินประกันเมื่อเกิดเหตุการณ์ข้อมูลรั่วไหลหรือระบบถูกโจมตี

ประกันไม่ได้อุดช่องโหว่ทางเทคนิคให้หายไป

ไม่ได้ลดความเสี่ยงที่ต้นเหตุ และไม่สามารถกู้คืนชื่อเสียงขององค์กรหรือความไว้วางใจของลูกค้าที่สูญเสียไปจากการถูกเจาะข้อมูลได้

1.2.5 Inherent Risk, Residual Risk, Risk Appetite & Tolerance

Inherent Risk (ความเสี่ยงดั้งเดิม)

ระดับความเสี่ยงที่มีอยู่ตามธรรมชาติก่อนที่จะมีการนำมาตรการควบคุมความปลอดภัยใด ๆ มาติดตั้งใช้งาน (Risk before controls)

Residual Risk (ความเสี่ยงที่หลงเหลือ)

ระดับความเสี่ยงที่ยังคงหลงเหลืออยู่หลังจากที่ได้ติดตั้งมาตรการควบคุมความปลอดภัยแล้ว (Risk after controls)

Residual Risk คือความเสี่ยงที่ประเมินใหม่หลังคำนึงถึงมาตรการควบคุม ไม่ใช่การลบคะแนนหรือเงินออกจากกันได้เสมอไป ต้องประเมินโอกาสเกิดและผลกระทบที่ยังเหลืออยู่ด้วยโมเดลและสเกลที่เหมาะสม

ตัวอย่าง: ก่อนติดตั้ง MFA ความเสี่ยงที่บัญชีจะถูกแฮกจากรหัสผ่านรั่วมีสูงมาก (Inherent Risk สูง) หลังติดตั้ง MFA ความเสี่ยงลดลงอย่างมาก แต่ยังคงมีโอกาสที่ผู้ใช้อาจถูกหลอกด้วยฟิชชิ่งแบบขั้นสูง (Adversary-in-the-Middle) อยู่บ้าง ความเสี่ยงที่ยังเหลือน้อยนี้เรียกว่า Residual Risk

Risk Appetite (ความเต็มใจรับความเสี่ยง)

ปริมาณและประเภทของความเสี่ยงในระดับกว้างที่องค์กรพร้อมและยินดีที่จะเปิดรับเพื่อบรรลุเป้าหมายและวิสัยทัศน์ทางธุรกิจ

Risk Tolerance (ขอบเขตความเสี่ยงที่ยอมรับได้)

ขอบเขตความเบี่ยงเบนที่ยอมให้เกิดขึ้นได้ในแต่ละโครงการหรือระบบย่อย เป็นระดับที่จำเพาะเจาะจงและวัดผลได้มากกว่า Risk Appetite

Objective 1.3: Understand governance concepts

การกำกับดูแลความมั่นคงปลอดภัยสารสนเทศ (Security Governance) คือการกำหนดทิศทาง โครงสร้างอำนาจหน้าที่ และกติกาเพื่อให้มั่นใจว่ากิจกรรมด้านความปลอดภัยสอดคล้องกับเป้าหมายทางธุรกิจและกฎหมาย

1.3.1 Security Governance Fundamentals

Security Governance คือระบบความสัมพันธ์และกระบวนการที่คณะกรรมการบริหารและผู้บริหารระดับสูงใช้ในการ ชี้นำ (Direct), ควบคุม (Control), และติดตามตรวจสอบ (Hold Accountable) การดำเนินงานด้านความปลอดภัย

แกนหลักของ Governance:

Governance = Direction + Oversight + Accountability

ข้อสอบมักถามความแตกต่าง:
ผู้บริหารระดับสูงที่ทำหน้าที่ Governance ไม่ใช่ผู้ที่ลงไปคอนฟิก Firewall หรือตั้งกฎบนเราเตอร์ด้วยตนเอง แต่เป็นผู้กำหนดนโยบาย ทิศทาง การจัดสรรงบประมาณ การแต่งตั้งผู้รับผิดชอบ และการตรวจสอบว่าองค์กรกำลังมุ่งหน้าไปในทิศทางที่ถูกต้อง

1.3.2 Laws and Regulations

กฎหมายและข้อบังคับคือ ข้อกำหนดที่มีผลผูกพันตามกฎหมาย (Legally Enforceable Requirements) หากฝ่าฝืนจะมีบทลงโทษทั้งทางแพ่ง ทางอาญา หรือค่าปรับมหาศาล

ตัวอย่างสำคัญที่มักพบในสื่อการเรียนและการสอบ:

GDPR (General Data Protection Regulation)

GDPR คุ้มครองข้อมูลส่วนบุคคลตามขอบเขตการใช้บังคับของกฎหมาย เช่น การประมวลผลในบริบทกิจกรรมของสถานประกอบการในสหภาพยุโรป หรือการเสนอสินค้า/บริการแก่บุคคลที่อยู่ในสหภาพยุโรปหรือเฝ้าติดตามพฤติกรรมของบุคคลที่เกิดขึ้นที่นั่นตามเงื่อนไข Article 3 การมีสัญชาติ EU เพียงอย่างเดียวไม่ใช่เกณฑ์ตัดสิน

HIPAA (Health Insurance Portability and Accountability Act)

กฎหมายในสหรัฐอเมริกาที่เน้นการคุ้มครองข้อมูลสุขภาพของผู้ป่วย (Protected Health Information - PHI)

PCI DSS (Payment Card Industry Data Security Standard)

มาตรฐานความปลอดภัยสำหรับองค์กรที่มีการจัดเก็บ ประมวลผล หรือส่งต่อข้อมูลบัตรเครดิต/เดบิต (แม้จะเป็นมาตรฐานของกลุ่มอุตสาหกรรม แต่มีผลบังคับใช้ผ่านสัญญาระหว่างธนาคารและผู้ให้บริการ)

หลักสำคัญเรื่องความสอดคล้อง (Applicability)

องค์กรแต่ละแห่งไม่ได้มีหน้าที่ต้องปฏิบัติตามกฎหมายหรือข้อบังคับทุกตัวบนโลก แต่ต้องพิจารณาจาก พื้นที่ตั้งทางภูมิศาสตร์ (Geography), อุตสาหกรรม (Industry), และประเภทของข้อมูล (Data Type) ที่ตนเองครอบครอง

1.3.3 Security Frameworks

Security Framework คือโครงสร้างหรือพิมพ์เขียวที่เป็นระบบ (Structured Blueprint) สำหรับใช้เป็นแนวทางในการสร้าง ปรับปรุง และประเมินโปรแกรมความปลอดภัยขององค์กร

ตัวอย่าง Framework ที่เป็นที่ยอมรับระดับสากล:

NIST Cybersecurity Framework (NIST CSF)

กรอบการดำเนินงานยอดนิยม ประกอบด้วยฟังก์ชันหลัก (Identify, Protect, Detect, Respond, Recover, Govern) ช่วยให้องค์กรประเมินช่องว่างและยกระดับความมั่นคงปลอดภัย

ISO/IEC 27001

มาตรฐานสากลว่าด้วยการจัดทำ นำไปปฏิบัติ บำรุงรักษา และปรับปรุง ระบบบริหารจัดการความมั่นคงปลอดภัยสารสนเทศ (Information Security Management System - ISMS) มุ่งเน้นการบริหารความเสี่ยงและกระบวนการอย่างต่อเนื่อง

CIS Controls (Center for Internet Security Controls)

รายการแนวทางปฏิบัติและมาตรการป้องกันความปลอดภัยที่ได้รับการจัดลำดับความสำคัญตามความเร่งด่วน (Prioritized Safeguards) เพื่อรับมือกับการโจมตีทางไซเบอร์ที่พบบ่อยที่สุด

1.3.5 Governance, Risk, and Compliance (GRC)

GRC คือการบูรณาการสามเสาหลักเข้าด้วยกันเพื่อให้องค์กรขับเคลื่อนไปข้างหน้าอย่างปลอดภัย:

Governance

ชี้ทิศทาง กำหนดความรับผิดชอบ และดูแลภาพรวมเชิงกลยุทธ์

Risk Management

ระบุและจัดการกับความไม่แน่นอนที่อาจส่งผลกระทบต่อเป้าหมายขององค์กร

Compliance

ปฏิบัติตามกฎหมาย ระเบียบ ข้อบังคับ และเงื่อนไขสัญญาอย่างถูกต้อง

ข้อคิดสำคัญสำหรับสอบ

"Compliance is not equivalent to complete security."

การปฏิบัติตามมาตรฐานครบถ้วน (100% Compliant) ไม่ได้รับประกันว่าองค์กรจะปลอดภัย 100% การตรวจสอบและประเมินความเสี่ยงที่แท้จริงตามบริบทของตนเองยังคงเป็นสิ่งที่ต้องทำควบคู่กันเสมอ

Objective 1.4: Understand cybersecurity controls

มาตรการควบคุมความปลอดภัย (Security Controls) คือเครื่องมือ กลไก และกระบวนการที่นำมาใช้ป้องกัน ตรวจจับ และตอบสนองต่อความเสี่ยง การวิเคราะห์ข้อสอบต้องแยกให้ออกระหว่าง Category (หมวดหมู่ของมาตรการ) และ Type / Function (หน้าที่การทำงานของมาตรการ)

1.4.1 Security Control Categories

การแบ่งหมวดหมู่ตามลักษณะของกลไกหรือสิ่งที่นำมาดำเนินการ:

01

Technical (Logical) Controls

มาตรการทางเทคนิค / ลอจิคัล

ใช้เทคโนโลยี ซอฟต์แวร์ อุปกรณ์ฮาร์ดแวร์ หรือการตั้งค่าระบบเพื่อควบคุมการเข้าถึงและปกป้องระบบคอมพิวเตอร์

ตัวอย่าง: Firewalls, IPS, Access Control Lists (ACLs), Data Encryption, Antivirus/EDR, ระบบ Password & MFA
02

Managerial (Administrative) Controls

มาตรการเชิงบริหารจัดการ

นโยบาย กฎระเบียบ การวางแผนเชิงยุทธศาสตร์ และการกำกับดูแลของฝ่ายบริหารเพื่อควบคุมพฤติกรรมองค์กร

ตัวอย่าง: Information Security Policies, การประเมินความเสี่ยง (Risk Assessment), การตรวจประวัติพนักงาน (Background Checks), การจัดชั้นความลับข้อมูล, การแบ่งแยกหน้าที่ (Separation of Duties)
03

Operational Controls

มาตรการเชิงปฏิบัติการ

กระบวนการ ขั้นตอนการทำงาน และกิจวัตรประจำวันที่ดำเนินการโดย คน (People & Daily Processes)

ตัวอย่าง: การอบรม Security Awareness Training, ขั้นตอนการทำ Backup & Recovery, การบริหารการเปลี่ยนแปลง (Change Management), การทำลายสื่อบันทึกข้อมูล
04

Physical Controls

มาตรการทางกายภาพ

สิ่งกีดขวาง โครงสร้าง และอุปกรณ์ทางกายภาพที่จับต้องได้ เพื่อปกป้องอาคาร สถานที่ ทรัพย์สิน และบุคลากร

ตัวอย่าง: ประตูนิรภัย ล็อคประตู รั้วกั้น (Fences), รปภ. (Guards), กล้องวงจรปิด (CCTV), ประตูควบคุมการผ่านเข้าออกสองชั้น (Mantrap/Access Control Vestibule), สัญญาณเตือนภัย (Alarms)

Recovery (กู้คืน) กู้คืนระบบจากชุด Backup, ดำเนินการตามแผน DRP, สลับไปศูนย์สำรอง (Alternate Site)
Key Concept: Overlap & Multi-Role Functions

มาตรการความมั่นคงปลอดภัยหนึ่งตัวสามารถทำหน้าที่ได้หลายฟังก์ชันพร้อมกัน: การจำแนกตามช่วงเวลา (Before / During / After) เป็นกรอบแนวคิดเพื่อความเข้าใจ ไม่ได้จำกัดว่ามาตรการหนึ่งจะถูกผูกขาดอยู่เพียงช่วงเวลาเดียว เช่น กล้องวงจรปิด (CCTV) เมื่อติดตั้งเด่นชัดจะทำหน้าที่เป็น Deterrent (ป้องปรามยับยั้งใจผู้บุกรุกก่อนเกิดเหตุ) ขณะเดียวกันก็ทำหน้าที่เป็น Detective (ตรวจจับและบันทึกภาพหลักฐานขณะเกิดเหตุ)

1. Deterrent (ยับยั้ง / ขัดขวาง)

มุ่งทำให้ผู้ประสงค์ร้ายเกิดความกลัว ไม่กล้าลงมือทำ หรือเปลี่ยนใจยอมแพ้ตั้งแต่ยังไม่เริ่ม

ตัวอย่าง: ป้ายเตือนมีกล้องวงจรปิดหรือห้ามบุกรุก, กล้องวงจรปิดที่ติดตั้งให้เห็นเด่นชัด, ป้อมยามพร้อมเจ้าหน้าที่ยืนตรวจ

คีย์เวิร์ดในข้อสอบ: Discourage, Warning signs, Visible presence, Don't even try
2. Preventive (ป้องกัน / สกัดกั้น)

ปิดกั้นหรือสกัดกั้นไม่ให้การกระทำที่ไม่พึงประสงค์เกิดขึ้นได้สำเร็จ

ตัวอย่าง: Firewall บล็อกพอร์ตที่ไม่ปลอดภัย, ประตูล็อค, การใช้ MFA สกัดการเข้าสู่ระบบ, การเข้ารหัสข้อมูล, Mantrap ป้องกันการเดินตาม

คีย์เวิร์ดในข้อสอบ: Block, Stop, Prevent, Keep out, Deny access
3. Detective (ตรวจจับ / แจ้งเตือน)

ตรวจจับ ค้นหา และแจ้งเตือนเมื่อมีเหตุการณ์ผิดปกติหรือมีการละเมิดเกิดขึ้น

ตัวอย่าง: Intrusion Detection Systems (IDS), Audit Logs, การเฝ้าระวังความผิดปกติ (Log Monitoring), Motion Detectors

คีย์เวิร์ดในข้อสอบ: Discover, Identify, Alert, Monitor, Audit trail
4. Corrective (แก้ไข / บรรเทาผลกระทบ)

แก้ไข ฟื้นฟู หรือกำจัดความเสียหายหลังจากที่เหตุการณ์เกิดขึ้นแล้ว

ตัวอย่าง: การกำจัดมัลแวร์ออกจากเครื่อง, การลง Patch แก้ไขช่องโหว่หลังถูกเจาะ, การกู้คืนระบบจาก Backup

คีย์เวิร์ดในข้อสอบ: Fix, Repair, Remediate, Restore system to normal
5. Compensating (ชดเชย / มาตรการทดแทน)

มาตรการทางเลือกที่นำมาใช้ทดแทนชั่วคราวหรือถาวรเมื่อไม่สามารถติดตั้งมาตรการควบคุมหลักตามมาตรฐานได้ (เนื่องจากข้อจำกัดทางเทคนิคหรือต้นทุน)

ตัวอย่าง: เซิร์ฟเวอร์รุ่นเก่าไม่รองรับ MFA จึงต้องใช้การเพิ่มการเฝ้าระวัง Log อย่างเข้มข้น ร่วมกับการจำกัดการเข้าถึงเฉพาะผ่าน VPN ภายในเท่านั้น

คีย์เวิร์ดในข้อสอบ: Alternative, Substitute, In place of primary control
6. Directive (ชี้นำ / สั่งการ)

ชี้แนะ บังคับ หรือสั่งการให้บุคคลปฏิบัติตามแนวทางที่ถูกต้อง

ตัวอย่าง: นโยบายความปลอดภัย, ขั้นตอนการทำงาน, ป้ายบอกทางหนีไฟ

7. Recovery (กู้คืน)

ขั้นตอนเฉพาะในการฟื้นฟูสภาพแวดล้อมและข้อมูลให้กลับมาให้บริการได้ตามปกติหลังวิกฤต เช่น Disaster Recovery Plan Execution

สูตรจำหน้าที่ของมาตรการ (Function Mnemonic; ไม่ใช่ลำดับตายตัว)

"กลัว (Deterrent) → กัน (Preventive) → เจอ (Detective) → แก้ (Corrective)"

1.4.3 Contextual & Overlapping Controls

หลักสำคัญที่สุดในข้อสอบ: มาตรการควบคุมหนึ่งตัวสามารถจัดอยู่ในหลายประเภทได้ ขึ้นอยู่กับ บริบทและการใช้งานในโจทย์นั้น ๆ (Context is King)

ตัวอย่างเปรียบเทียบการประยุกต์ใช้ตามบริบท:

กล้องวงจรปิด (CCTV)
  • ติดตั้งกล้องขนาดใหญ่ไว้หน้าประตูทางเข้าอย่างเด่นชัดเพื่อให้คนเห็น → ทำหน้าที่เป็น Deterrent Control
  • เจ้าหน้าที่นั่งดูกล้องสดเพื่อเฝ้าระวังผู้บุกรุก หรือเปิดเทปย้อนหลังสืบสวน → ทำหน้าที่เป็น Detective Control
  • ในแง่หมวดหมู่เครื่องมือ → จัดเป็น Physical Category
ไฟร์วอลล์ (Firewall)
  • ทำหน้าที่ Drop หรือ Block แพ็กเก็ตที่ผิดปกติ → ทำหน้าที่เป็น Preventive Control
  • ทำหน้าที่บันทึก Connection Logs และแจ้งเตือน Alert → ทำหน้าที่เป็น Detective Control
  • ในแง่หมวดหมู่เครื่องมือ → จัดเป็น Technical Category
วิธีวิเคราะห์ข้อสอบเรื่อง Security Controls 3 สเต็ป
  1. โจทย์ถามหา หมวดหมู่ (Category) หรือถามหา หน้าที่ (Type/Function)?
  2. มาตรการนั้นทำงาน ก่อน (Before), ระหว่าง (During), หรือหลัง (After) เกิดเหตุ? ใช้เวลาเป็นบริบทประกอบ ไม่ใช่เกณฑ์ตายตัว เพราะ Detective อาจพบย้อนหลังและ Corrective อาจเริ่มขณะเกิดเหตุ
  3. เจตนาหลักที่โจทย์เน้นคือ ยับยั้งใจ, สกัดกั้น, ค้นหาตรวจจับ, หรือแก้ไขปัญหา?

Objective 1.5: Maintain professional and ethical conduct

บุคลากรด้านความมั่นคงปลอดภัยไซเบอร์มักถือครองสิทธิ์ระดับสูงในระบบ หน้าที่ด้านจริยธรรม ความรอบคอบระมัดระวัง และการปฏิบัติตามประมวลจริยธรรมของสถาบันจึงเป็นข้อกำหนดที่ไม่อาจละเลยได้

1.5.1 Professional Code of Conduct & Authority Boundaries

หลักจรรยาบรรณวิชาชีพกำหนดแนวทางการปฏิบัติตนของผู้เชี่ยวชาญด้านไซเบอร์ โดยยึดถือหลักความซื่อสัตย์ ความน่าเชื่อถือ และความรับผิดชอบ

หลักการเรื่องสิทธิ์และขอบเขตอำนาจ (Technical Access ≠ Business Authorization):

การที่ผู้ดูแลระบบมีความสามารถทางเทคนิค (Technical Capability) ในการเข้าถึงระบบได้ทุกอย่าง ไม่ได้แปลว่าบุคคลนั้นมีสิทธิ์อันชอบธรรม (Authorized Right) ในการเข้าไปดูหรือแก้ไขข้อมูลเหล่านั้นตามอำเภอใจ

ตัวอย่างคลาสสิก (Technical Access ≠ Business Authorization):

นาย ก. เป็น Domain Administrator ของบริษัท มีสิทธิ์เข้าถึงฮาร์ดดิสก์ของแผนก HR ได้โดยตรงทางเทคนิค แต่นาย ก. ไม่มีสิทธิ์ เข้าไปเปิดอ่านไฟล์ประวัติเงินเดือนหรือข้อมูลสุขภาพของเพื่อนร่วมงาน เว้นแต่จะมีคำสั่งหรือวัตถุประสงค์ทางธุรกิจที่ได้รับอนุมัติอย่างเป็นทางการ

1.5.2 Due Care vs. Due Diligence

สองคำนี้เป็นคำศัพท์ทางกฎหมายและความปลอดภัยที่มักทำให้สับสน:

1. Due Care (ความระมัดระวังตามสมควร)

การลงมือกระทำในสิ่งที่สมเหตุสมผลและรับผิดชอบ เพื่อปกป้องทรัพย์สินและลดความเสี่ยง

แก่นสำคัญในข้อสอบ: Due Care = DO / Take Action

ตัวอย่างการปฏิบัติ Due Care:

  • การลง Patch อุดช่องโหว่ทันทีที่ได้รับแจ้ง
  • การบังคับใช้นโยบายรหัสผ่านที่รัดกุม
  • การติดตั้งโปรแกรมป้องกันไวรัสบนเครื่องคอมพิวเตอร์
  • การฝึกอบรมพนักงานเรื่อง Phishing

2. Due Diligence (ความพากเพียรตรวจสอบอย่างรอบคอบ)

การสืบค้น ตรวจสอบ ประเมินผล และติดตามสถานะความเสี่ยงอย่างต่อเนื่อง เพื่อให้รู้ว่าสิ่งที่ทำอยู่นั้นเหมาะสมและมีประสิทธิภาพจริงหรือไม่

แก่นสำคัญในข้อสอบ: Due Diligence = CHECK / Verify / Investigate

ตัวอย่างการปฏิบัติ Due Diligence:

  • การรัน Vulnerability Scan ตรวจสอบจุดอ่อนของเซิร์ฟเวอร์
  • การทำ Risk Assessment ประจำปี
  • การตรวจสอบประวัติและสถานะความปลอดภัยของ Vendor ก่อนเซ็นสัญญา
  • การตรวจสอบผลการสแกนหลังจากการ Patch ว่าช่องโหว่ถูกปิดสนิทจริงหรือไม่

วงจรการทำงานร่วมกันและตารางคำกริยาแยกแยะในข้อสอบ:

01
DUE DILIGENCE (CHECK)
"Knowing what is right" · สืบค้นและตรวจสอบความจริง

02
DUE CARE (DO)
"Doing what is right" · ปฏิบัติการป้องกันตามมาตรฐานวิญญูชน

ลงมือปฏิบัติแก้ไขและควบคุมความเสี่ยงอย่างสมเหตุสมผล เช่น ติดตั้ง Security Patch อุดช่องโหว่ทันที, บังคับใช้ MFA, เข้ารหัสข้อมูลสำคัญ

↓ ตรวจสอบซ้ำยืนยันผล ↓
03

"Validating the outcome" · ตรวจซ้ำยืนยันประสิทธิผล

STRICT ORDER OF PRECEDENCE

จรรยาบรรณวิชาชีพ ISC2 มี 4 ข้อ เรียงตามลำดับความสำคัญเด็ดขาด: หากเกิดข้อขัดแย้ง ข้อก่อนหน้าจะมีอำนาจเหนือกว่าข้อถัดไปเสมอ (Canon 01 > 02 > 03 > 04)

01
CANON 1: SOCIETY & INFRASTRUCTURE
PRIORITY 1 (สูงสุด) · ปกป้องสังคมและสาธารณชน

"Protect society, the common good, necessary public trust, and infrastructure." — ปกป้องสังคม ประโยชน์ส่วนรวม ความไว้วางใจของสาธารณะ และโครงสร้างพื้นฐานสำคัญของชาติ (หากขัดแย้งกับคำสั่งองค์กร ให้ยึดถือสังคมก่อนเสมอ)

↓ มีอำนาจบังคับเหนือกว่า (Supersedes) ↓
02
CANON 2: HONOR & LEGALITY
PRIORITY 2 · ซื่อสัตย์ ยุติธรรม และเคารพกฎหมาย

"Act honorably, honestly, justly, responsibly, and legally." — ประพฤติตนอย่างสมเกียรติ ซื่อสัตย์ ยุติธรรม มีความรับผิดชอบ และเคารพกฎหมายอย่างเคร่งครัด ไม่ละเมิดกฎหมายเพื่อประโยชน์ส่วนตนหรือผู้อื่น

↓ มีอำนาจบังคับเหนือกว่า (Supersedes) ↓
03
CANON 3: DILIGENT SERVICE TO PRINCIPALS
PRIORITY 3 · ปฏิบัติงานต่อนายจ้าง/ลูกค้าอย่างเชี่ยวชาญ

"Provide diligent and competent service to principals." — ให้บริการด้วยความขยันขันแข็งและเปี่ยมด้วยสมรรถนะแก่นายจ้างหรือลูกค้า โดยไม่ละเมิดข้อ 1 หรือข้อ 2

↓ มีอำนาจบังคับเหนือกว่า (Supersedes) ↓
04
CANON 4: ADVANCE THE PROFESSION
PRIORITY 4 · ส่งเสริมและปกป้องวิชาชีพ

"Advance and protect the profession." — ส่งเสริมและปกป้องชื่อเสียงของวิชาชีพความมั่นคงปลอดภัยสารสนเทศ แบ่งปันความรู้ ยกระดับมาตรฐาน และไม่กระทำการใดที่ทำให้วิชาชีพเสื่อมเสีย

กฎลำดับความสำคัญ (Strict Order of Precedence): ข้อ 1 ถึง 4 เรียงตามลำดับความสำคัญจากสูงสุดลงไปอย่างเคร่งครัด หากเกิดความขัดแย้งทางหน้าที่ ผลประโยชน์ หรือคำสั่งของผู้ว่าจ้าง Canon ลำดับก่อนหน้าจะมีความสำคัญเหนือกว่าเสมอ
01

Canon 1: Protect society, the common good, necessary public trust and confidence, and the infrastructure

Priority 1 (สำคัญสูงสุด)

ปกป้องสังคม ประโยชน์ส่วนรวม ความไว้วางใจของสาธารณะ และโครงสร้างพื้นฐานสำคัญ: เป็นข้อที่มีลำดับความสำคัญสูงสุดเหนือกฎข้ออื่นทั้งหมด หากผลประโยชน์ขององค์กรหรือคำสั่งของผู้ว่าจ้างขัดแย้งกับความปลอดภัยของสาธารณะ ต้องเลือกความปลอดภัยของสังคมเป็นอันดับแรกเสมอ

02

Canon 2: Act honorably, honestly, justly, responsibly, and legally

Priority 2

ประพฤติตนอย่างมีเกียรติ ซื่อสัตย์ ยุติธรรม มีความรับผิดชอบ และถูกต้องตามกฎหมาย: ปฏิบัติตามกฎหมายอย่างเคร่งครัด ไม่โกหก ไม่บิดเบือนข้อเท็จจริง และรักษาความโปร่งใสในวิชาชีพ (ข้อสังเกต: Canon 2 กำหนดหน้าที่เหล่านี้ร่วมกัน ไม่ควรอนุมานลำดับเหนือกว่ากันจากลำดับคำในประโยค การกระทำที่ไม่ผิดกฎหมายอาจยังขัดจริยธรรมหากเป็นการหลอกลวง บิดเบือนข้อเท็จจริง หรือไม่เป็นธรรม)

03

Canon 3: Provide diligent and competent service to principals

Priority 3

ให้บริการแก่นายจ้างหรือลูกค้าอย่างขยันขันแข็ง รอบคอบ และเต็มความสามารถ: รักษาความลับและผลประโยชน์ที่ชอบธรรมของผู้ว่าจ้าง ไม่นำข้อมูลลับไปแสวงหาผลประโยชน์ส่วนตน และไม่รับงานที่ตนขาดความเชี่ยวชาญโดยไม่แจ้งล่วงหน้า

04

Canon 4: Advance and protect the profession

Priority 4

ส่งเสริม ยกระดับ และปกป้องชื่อเสียงของวิชาชีพ: ร่วมแลกเปลี่ยนความรู้ ยกระดับมาตรฐานวิชาชีพด้านไซเบอร์ และไม่กระทำการใดที่ทำให้เกียรติภูมิของวิชาชีพเสื่อมเสีย

สูตรจำตัวอักษรย่อ (Mnemonic):
"S - A - P - P"
Society → Act honorably → Principals → Profession

1.5.4 Concept Distinctions, Scenarios & Quick Review

1. ตาราง 12 คู่คำที่มักสับสนในข้อสอบ (Concept Distinctions Matrix)

1. Threat vs. Vulnerability
Threat (ภัยคุกคาม)
บุคคล สิ่ง หรือเหตุการณ์ภายในหรือภายนอกที่อาจก่ออันตราย (Insider, Hacker, Malware, Flood)
Vulnerability (ช่องโหว่)
จุดอ่อนภายในระบบที่เปิดโอกาสให้ถูกโจมตี (Unpatched Server, Weak Password)
2. Risk vs. Impact
Risk (ความเสี่ยง)
การพิจารณาโอกาสเกิด (Likelihood) ร่วมกับผลกระทบ (Impact) จากเหตุการณ์ที่ไม่แน่นอน
Impact (ผลกระทบ)
ขนาดหรือมูลค่าความเสียหายที่เกิดขึ้นจริงเมื่อระบบถูกโจมตี
3. Authentication vs. Authorization
Authentication (พิสูจน์ตัวตน)
ยืนยันว่าคุณคือบุคคลนั้นจริงหรือไม่ ("Prove who you are")
Authorization (กำหนดสิทธิ์)
ตัดสินว่าคุณมีสิทธิ์ทำอะไรกับระบบได้บ้าง ("What can you do")
4. Confidentiality vs. Privacy
Confidentiality (ความลับ)
ป้องกันไม่ให้ข้อมูลลับถูกเปิดเผยแก่ผู้ไม่มีสิทธิ์
Privacy (ความเป็นส่วนตัว)
สิทธิและการคุ้มครองข้อมูลส่วนบุคคล (PII) ตามกฎหมายและเจตนารมณ์ของเจ้าของข้อมูล
5. Integrity vs. Availability
Integrity (ความถูกต้อง)
ข้อมูลต้องไม่ถูกแก้ไขหรือทำลายโดยมิชอบ ("Can I trust the data?")
Availability (ความพร้อมใช้)
ระบบและข้อมูลพร้อมให้ผู้มีสิทธิ์เข้าถึงตามเวลาที่จำเป็นและข้อกำหนดบริการ ("Can I access it?")
6. Hashing vs. Encryption
Hashing
ฟังก์ชันทางเดียว (One-way) ใช้คำนวณค่าเพื่อตรวจสอบความถูกต้อง ไม่สามารถถอดรหัสกลับได้
Encryption
ฟังก์ชันสองทาง (Two-way) เข้ารหัสเพื่อรักษาความลับ และถอดรหัสกลับได้ด้วยกุญแจที่ถูกต้อง
7. Preventive vs. Detective
Preventive (ป้องกัน)
ปิดกั้นหรือสกัดกั้นการโจมตีไม่ให้เกิดขึ้น (Firewall drop, Door lock, MFA)
Detective (ตรวจจับ)
ตรวจจับ ค้นหา และแจ้งเตือนเมื่อเกิดความผิดปกติ (IDS, Log monitor, Motion sensor)
8. Corrective vs. Recovery
Corrective (แก้ไข)
แก้ไข เยียวยา หรือกำจัดมัลแวร์และอุดช่องโหว่เพื่อลดความเสียหาย
Recovery (กู้คืน)
ฟื้นฟูระบบและข้อมูลให้กลับมาให้บริการตามปกติหลังวิกฤต (DRP restore)
9. Risk Transfer vs. Risk Mitigation
Risk Transfer (โอนความเสี่ยง)
ย้ายเฉพาะภาระทางการเงินไปยังบุคคลภายนอก (ประกันภัยไซเบอร์)
Risk Mitigation (ลดความเสี่ยง)
ติดตั้งมาตรการทางเทคนิค/กระบวนการเพื่อลดโอกาสเกิดหรือผลกระทบโดยตรง
10. Policy vs. Procedure
Policy (นโยบาย)
ทิศทางภาพกว้าง วิสัยทัศน์ และความคาดหวังของผู้บริหารระดับสูง (WHAT & WHY)
Procedure (ขั้นตอนปฏิบัติ)
ขั้นตอนการลงมือปฏิบัติทีละขั้นแบบเป็นลำดับสำหรับผู้ใช้งาน (HOW)
11. Due Care vs. Due Diligence
Due Care
การลงมือกระทำในสิ่งที่สมเหตุสมผลและรับผิดชอบเพื่อปกป้องทรัพย์สิน (DO / Take Action)
Due Diligence
การสืบค้น ตรวจสอบ ประเมินผล และติดตามสถานะความเสี่ยงอย่างรอบคอบ (CHECK / Investigate)
12. Zero Trust vs. Defense in Depth
Zero Trust
ปรัชญาความเชื่อมั่นและการเข้าถึง ("Never Trust, Always Verify" ตรวจสอบทุกบริบท)
Defense in Depth
ยุทธศาสตร์สถาปัตยกรรมความปลอดภัยที่วางเกราะป้องกันหลายชั้นสอดประสานกัน

2. ตัวอย่างโจทย์สถานการณ์ทบทวน (Review Scenarios)

Scenario 1 CIA Triad

สถานการณ์: ผู้โจมตีสามารถแก้ไขตัวเลขเงินเดือนในฐานข้อมูลโดยที่ระบบไม่ส่งสัญญาณเตือนใด ๆ

คำถาม: เหตุการณ์นี้ส่งผลกระทบต่อหลักการใดของ CIA มากที่สุด?

เฉลยและเหตุผล:

Integrity (เพราะข้อมูลถูกแก้ไขดัดแปลงให้ผิดเพี้ยนไปจากความจริง)

Scenario 2 Access Control

สถานการณ์: พนักงานกรอกรหัสผ่านผ่านเรียบร้อยแล้ว แต่เมื่อคลิกเปิดไฟล์โฟลเดอร์การเงิน ระบบแจ้งว่าไม่สามารถเข้าถึงได้

คำถาม: ปัญหานี้เกี่ยวข้องกับขั้นตอนใดของระบบควบคุมการเข้าถึง?

เฉลยและเหตุผล:

Authorization (เนื่องจาก Authentication ยืนยันตัวตนผ่านแล้ว แต่สิทธิ์การเข้าถึงไม่อนุญาต)

Scenario 3 Risk Management

สถานการณ์: บริษัทแห่งหนึ่งตัดสินใจซื้อกรมธรรม์ประกันภัยไซเบอร์ (Cyber Insurance) วงเงิน 50 ล้านบาท เพื่อคุ้มครองกรณีข้อมูลรั่วไหล

คำถาม: จัดเป็นกลยุทธ์การบริหารความเสี่ยงรูปแบบใด?

เฉลยและเหตุผล:

Risk Transfer (Sharing) (การโอนย้ายภาระทางการเงินไปยังบริษัทประกันภัย)

Scenario 4 Professional Conduct

สถานการณ์: เจ้าหน้าที่ความปลอดภัยนำโปรแกรม Vulnerability Scanner มาสแกนเซิร์ฟเวอร์ทั้งหมดในองค์กรเพื่อทำรายงานความเสี่ยง

คำถาม: การกระทำนี้สะท้อนถึงหลักการใดระหว่าง Due Care กับ Due Diligence?

เฉลยและเหตุผล:

Due Diligence (เนื่องจากเป็นการตรวจสอบ สืบค้น และประเมินความเสี่ยงอย่างรอบคอบ)

Scenario 5 Professional Conduct

สถานการณ์: เมื่อระบบสแกนพบช่องโหว่ระดับวิกฤต ทีมงานจึงเร่งดาวน์โหลดและติดตั้ง Security Patch ทันที

คำถาม: การลงมือติดตั้ง Patch สะท้อนถึงหลักการใด?

เฉลยและเหตุผล:

Due Care (เป็นการลงมือปฏิบัติเพื่อปกป้องทรัพย์สิน)

Scenario 6 Risk Analysis

สถานการณ์: ผู้บริหารพิจารณาแล้วพบว่า ค่าใช้จ่ายในการซื้ออุปกรณ์ป้องกัน DDoS มูลค่าปีละ 1,000,000 บาท สูงกว่าความเสียหายเฉลี่ยต่อปีที่คาดว่าจะเกิดขึ้น (ALE = 50,000 บาท) ผู้บริหารจึงลงนามอนุมัติไม่ซื้ออุปกรณ์และยอมรับความเสี่ยงนี้

คำถาม: จัดเป็นกลยุทธ์การบริหารความเสี่ยงรูปแบบใด?

เฉลยและเหตุผล:

Risk Acceptance (การยอมรับความเสี่ยงอย่างเป็นทางการเมื่อต้นทุนสูงกว่าผลประโยชน์)

Scenario 7 Security Architecture

สถานการณ์: องค์กรบังคับใช้นโยบายว่า แม้พนักงานจะล็อกอินผ่านคอมพิวเตอร์ที่ต่อสาย LAN ภายในอาคารสำนักงานใหญ่ ทุกคนยังต้องยืนยันตัวตนผ่าน MFA และระบบจะตรวจสอบสุขภาพของเครื่องก่อนอนุญาตให้เข้าถึงคลาวด์

คำถาม: สอดคล้องกับแนวคิดทางสถาปัตยกรรมความปลอดภัยใด?

เฉลยและเหตุผล:

Zero Trust Architecture (Never Trust, Always Verify ไม่ให้ความเชื่อถือโดยปริยายเพียงเพราะอยู่ภายในเครือข่าย)

Scenario 8 Security Controls

สถานการณ์: ป้ายเตือนขนาดใหญ่เขียนว่า "พื้นที่หวงห้าม บันทึกภาพด้วยกล้องวงจรปิดตลอด 24 ชั่วโมง ผู้บุกรุกจะถูกดำเนินคดีตามกฎหมาย"

คำถาม: ป้ายเตือนนี้ทำหน้าที่เป็น Security Control ประเภทใด?

เฉลยและเหตุผล:

Deterrent Control (มุ่งยับยั้งใจและขัดขวางไม่ให้ผู้ประสงค์ร้ายกล้าลงมือกระทำผิด)
